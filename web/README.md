# HospitalGym web app

Next.js (App Router) + TypeScript + React Three Fiber + Zustand + Tailwind. The product is the twin → simulate →
optimize loop for a hospital emergency department. The bare address `/` is a landing page (what this is, how it works,
results so far, what each page does); the modes are Optimize, Play, Watch, Compare and Trade-off. One 3D hospital
scene, drawn entirely from the layout JSON, is reused by Play, Watch, Compare and Trade-off. Everything is built
against `contracts/` (`api.md`, `snapshot`, `layout`, `rollout`, `metrics`, `actions`, `catalog`).

User-facing text is US English. Server strings recorded earlier in British English are normalized on the way in
(`us()` in `lib/optimize.ts`).

## Landing page

`components/modes/HomeView.tsx`, numbers from `lib/home.ts`. Every figure is simulated. Each group starts from values
recorded when the page was written and is replaced by what the API returns, and is tagged "live" or "recorded":

| Group | Live source | Recorded fallback |
|---|---|---|
| Recommended plan (same budget, better flow) | `GET /api/headline/{hospital}` → `objectives.same_budget_better_flow`, selected candidate, `normal_week` | yes |
| Twin vs. published figures | published side from `GET /api/validation` targets; the twin side is the recorded calibration check | yes |
| Ask for anything | `GET /api/optimize` (latest finished "profit first" and "maximize waiting" searches) and their results | yes |
| What each resource is worth | none (the attribution summary is about 1 MB) | always recorded |

The `same_service_lower_cost` objective is deliberately not shown there.

## Run

```bash
cd web
pnpm install
pnpm dev            # http://localhost:3000
pnpm build          # production build, type-checked
pnpm start          # serve the build on :3000
```

- `NEXT_PUBLIC_API_URL` sets the server (default `http://localhost:8000`). For one browser tab you can also append
  `?api=http://host:port` to the address.
- Deep links: `/?mode=optimize|play|watch|compare|tradeoff` (no `mode` = the landing page; the logo goes back to it), `&rollout=<id>` (Watch), `&a=<id>&b=<id>` (Compare),
  `&gfx=low` (no shadows or antialiasing, for weak GPUs).

## Online and offline

Every call goes through `lib/api.ts`. If the server does not answer, the same call resolves from the files in
`public/fixtures/` and the result is marked `fixture`. The status pill in the top bar shows "Live" or
"Offline · sample data", and its popover lists the simulator and data services from `/api/status`.
Fixture data is labelled wherever it appears (chips on panels, a banner on the trade-off chart).

`public/fixtures/` is generated by `pnpm fixtures` (`scripts/make-fixtures.mjs`) from `contracts/fixtures/`,
`contracts/*.yaml`, `catalog/*.yaml` and `catalog/hospitals/rwjuh_nb.layout.json`:

| File | Stands in for |
|---|---|
| `status.json`, `enums.json`, `metrics.json`, `scenarios.json`, `hospitals.json`, `managers.json` | the endpoints of the same name |
| `catalog.json`, `catalog-refs.json` | `/api/catalog`, `/api/catalog/ref/*` (built from the real `catalog/*.yaml`) |
| `layout.fixture.json`, `rwjuh_nb.layout.json` | `/api/layout/{id}` |
| `rollouts.json`, `rollout.fixture.json`, `rollout.fixture_b.json` | `/api/rollouts`, `/api/rollouts/{id}` |
| `results.json` | `/api/results` |

Two of these are invented for layout work and say so on screen: `rollout.fixture_b.json` is a mechanical edit of the
contract fixture so Compare has a second manager, and the points in `results.json` are typed by hand. Neither is a
simulator or evaluation result.

Offline, Play replays the fixture rollout (knob changes are shown as queued but nothing is simulated), and the human
run is kept in this browser's localStorage instead of being POSTed.

### Trying the live path without the real server

`pnpm mock-server` (`scripts/mock-server.mjs`, port 8010) implements the HTTP and websocket shapes in
`contracts/api.md` with a toy patient flow. It exists to exercise the client; it is not the simulator.
Open `http://localhost:3000/?mode=play&api=http://localhost:8010`.

## What was checked against the real server

With `server/` running on :8000 the screenshot script was run with `--api http://localhost:8000`: status, lists,
layout, catalog refs, the fixture rollout, a live Play run over the websocket (knob queued, stop, final summary, human
run POSTed and shown on the trade-off chart), the validation card, and a live Compare (two sockets, same scenario and
seed, two managers). Server behaviours handled: `hour` acknowledgements with empty metrics are not plotted; `pending`
is read as "not yet applied" and current settings come from `snapshot.kpis.settings`; several `hour` messages may
arrive between snapshots at high speed; `stop` is awaited through `summary.final`; unknown catalog refs (404) show as
"no catalog entry" rather than a fixture; manager and rollout lists are re-read on every mode change.

Round 2 checks against the real server (all through `scripts/screenshots.mjs --api http://localhost:8000`):
`inject` for all four events (acknowledged, start at the next hour, appear in the feed and as toasts), manager
hand-over and take-back mid-run (the panel shows who is in charge with the kind label, from the server's `hour`
messages), 48x speed, and a structural change (`--only structural`, several minutes: the human queues "add bays" and
"add ward beds", they apply at the 28-day boundary, and the building is redrawn when the `layout` message arrives).

Other behaviour worth knowing:
- A bay the simulator reports as occupied with nobody in it is shown as "Held": its patient is away for a test. The
  inspector names that patient when the snapshots seen so far show which one it is.
- Catalog definitions list a variant's own attributes first; attributes shared by the whole entity type are collapsed
  below. Attributes carrying `mixed_provenance` get a "mixed" chip and the note.
- Charts with more than 120 hourly points default to one point per day (mean, shaded from the day's lowest to highest
  hour) with a "72 h" hourly window around the playhead as the alternative.
- The trade-off chart offers a "Staffing cost" x-axis only when result rows carry a labour-cost metric (found by key
  name), and marks a human run shorter than the evaluation protocol as not comparable.
- "Demo tour" (top bar) is a short walk through the product (`lib/tour.ts`): a normal day under current practice,
  the Optimize page, the recommended plan at work, current practice against that plan on the same patients, the same
  under a flu surge, and the trade-off chart. It starts only when the button is pressed. A step whose recordings are
  not there is left out silently. Going to another mode by hand ends it. The card floats bottom-right over the 3D
  modes and sits in the page flow on Optimize, so it never covers a control. Arrow keys move, Escape leaves.
- Speed "Max" asks the server for 600 ticks a second; it delivers what it can and skips snapshots above about 30 a second.

Round 3 (after the QA pass):
- **A live run survives reloads and mode switches.** Its `run_id` is kept in sessionStorage; Play rejoins it with the
  websocket `attach` message. `/?run_id=..&patient_id=..` lands in Play on that run with the patient selected. If the server no longer has the
  run, Play says so and offers a fresh start. Changing scenario or hospital mid-run asks before ending the run.
- **Never run `pnpm build` or a second `next dev` in `web/` while a dev server is running**: both write `web/.next`
  and break the running server.
- The top bar has two rows on a desktop and fits from 1280 px; on a phone the tour button is under "More".
- When the API is unreachable a banner says so in every mode, tags read "fixture", and the app reloads live data by
  itself when the API answers again.
- Watch stops at the end of each recorded window (next window / replay) instead of looping; the windows are listed
  under the chart; a click outside them moves only the chart cursor and says there is no 3D recording for that hour.
- What is said about a manager is composed in `lib/story.ts` from `/api/managers` and `/api/results` only, never typed
  in: what a learned agent was rewarded for (its reward weights), how it was trained (from its label and note), the
  held-out verdict against its tuned heuristic with the paired margin and interval on that objective's score, and the
  mean wait, walk-outs and deaths per 10k of both. A margin under 0.01 is called "effectively the same", never
  "beats". The same sentence is used in Watch, Compare, Trade-off, the tour and the Play "In charge" card.
- Plan names are shortened with the distinguishing part first (`shortManager`: "Lowest cost · PPO cloned",
  "Shortest wait · tuned plan", "Cost dial · PPO conditioned", "Current practice" for the baseline); the server's
  full label is the hover title. Primary text says "plan" and "fresh simulated patients"; the precise terms stay in
  detail text.
  On the trade-off chart managers that share a spot get one label, a count badge, a tooltip listing all of them, and
  clicks that step through them. Recorded Compare defaults to current practice against the recommended plan
  (`tuned_same_budget`) when both recordings exist, else lowest cost against shortest wait.
- People in the scene have enlarged invisible click targets and win over the room behind them. The idle camera sways
  about twenty degrees instead of circling, so floor labels are never read from behind.

Compare has two sources: recorded rollouts (one shared replay clock) or "Run live" (two live simulations; each runs
on its own clock, so they can drift a few ticks apart).

## Structure

```
app/                 layout, the single app page
components/
  App.tsx            mode switching, boot
  scene/             the 3D scene (client-only, loaded with ssr: false)
    build.ts         layout JSON -> primitives (floors, walls, beds, scanners, roads, trees)
    Building.tsx     instanced meshes for those primitives, floor labels, context buildings
    People.tsx       patients and staff as two instanced meshes, interpolated by entity id
    Ambulances.tsx, SelectionBox.tsx (corner brackets + pill), CameraRig.tsx (orbit, drift, fly-to)
  modes/             HomeView (landing), OptimizeView, OpsView (Play + Watch), PlayPanel, WatchPanel, CompareView, TradeoffView
  optimize/          GoalPicker, SearchProgress, PlanResult
  ui/                TopBar, KPI cards, Inspector, EntityList, Journey stepper, Timeline, LineChart, Toasts, Tour
lib/
  types.ts           the contracts as TypeScript
  api.ts             typed client + fixture fallback
  feed.ts            a "feed": one stream of snapshots with its header, layout, hourly series, decisions
  replay.ts          plays recorded rollouts into one or two feeds on a shared clock
  live.ts            WS /ws/sim client
  session.ts         owns the feeds and whichever writer is active; Play controls; human-run POST
  ui.ts              interface state (mode, selection, speed, toasts, tour, ...)
  nav.ts             mode navigation (what each mode loads)
  tour.ts            the guided demo's steps
  home.ts            landing-page numbers: recorded values, replaced by live ones
  optimize.ts        client for the optimize jobs, labels, US-English normalizer
  describe.ts        titles, pill labels, room state ("Held") for a selection
scripts/
  make-fixtures.mjs  builds public/fixtures
  mock-server.mjs    stand-in server for the live path
  screenshots.mjs    headless Playwright run that saves PNGs to overnight/screenshots/
```

How the scene stays fast: every box, rounded box and cylinder in the building is one of four instanced meshes; people
are two instanced meshes (bodies, heads). Positions are interpolated per frame inside the render loop without React
re-renders; panels read the feed at most four times a second. The shadow map refreshes on alternate frames.

Conventions the scene relies on: metres, `x` east, `z` south; patients lie down when they are in a bed-type room in an
in-bay state; people who appear or leave scale in and out over 0.4 s; a jump in the stream (scrub, restart) snaps
instead of gliding. Campus buildings in `site.buildings` are context: a footprint under 1 m high is drawn as a flat
ground slab, the others as low massing blocks (22 % of real height, capped at 7 m) so they never hide the department.

## Screenshots

```bash
PLAYWRIGHT_BROWSERS_PATH=.playwright pnpm exec playwright install chromium   # once
pnpm dev                                    # or pnpm start
node scripts/screenshots.mjs http://localhost:3000            # software GL (SwiftShader), slow
node scripts/screenshots.mjs http://localhost:3000 --gpu      # the machine's GPU, fast
node scripts/screenshots.mjs --gpu --offline                  # force the fixture fallback (files web-*.png)
node scripts/screenshots.mjs --gpu --api http://localhost:8000   # against a running server (files web-live-*.png)
```

The script also checks behaviour and prints problems: search selection, list selection, a click in the 3D scene,
timeline scrubbing, Play start/stop, the trade-off click-through, the phone drawer, and that switching hospital
redraws the building.

## No layout shift

Hints in the Optimize goal picker are always present and of fixed height: the line under a measure changes its words,
never its size; "Clear" and the tie buttons are always in place (disabled or invisible when they do not apply); the
empty priorities box is as tall as two goals. The pause/step control in the top bar is likewise always there.

Assumptions that need the simulator's confirmation are listed in `CONTRACT_REQUESTS.md`.
